# Build `jarvis-code` — a local, sandboxed coding agent

You are building a real, open-source CLI coding agent named **`jarvis-code`** that installs a command called **`jarvis`**. Think "Claude Code, but mine": strict sandboxing, explicit permission modes, multi-provider model support, local/offline voice I/O, live voice steering, sub-agent orchestration, and a clone-and-run GitHub developer experience.

This is not a demo. Build the foundation of a production-quality tool.

---

## How I want you to work

1. **Build in the phase order below.** Do not jump ahead. Each phase has a "Done when" checklist. Do not start a phase until the previous one's tests pass.
2. **Security first.** The sandbox layer (Phase 2) and config/secrets layer (Phase 3) come before anything fun. Voice is last.
3. **Test as you go.** Every phase that ships logic ships unit tests in the same phase. Run `pytest -q` before declaring a phase done. Never leave the tree red.
4. **Commit per phase** with a clear message (e.g. `feat(sandbox): canonical path enforcement + symlink escape tests`). Keep commits scoped.
5. **Write a `CLAUDE.md`** in the repo root in Phase 0 capturing the invariants below, the layout, and the test command, so future sessions stay aligned. Update it as the design firms up.
6. **Maintain a running plan/todo.** At the start of each phase, restate the goal and the acceptance checklist, then work it down.
7. **Ask me before diverging** on anything that breaks an invariant, changes the public CLI surface, or adds a required (non-optional) third-party dependency. Otherwise make reasonable engineering calls and note them.
8. **Keep it small.** Small typed functions, narrow modules, clear seams. Prefer boring, readable code over cleverness.
9. **Graceful degradation, not crashes.** Missing optional deps (Piper, whisper, a mic, a provider key) must produce a clear, actionable message — never a stack trace and never a hard failure of unrelated features.

When a phase is done, give me a 3-5 line summary: what you built, what's tested, what's stubbed/deferred, and what's next.

## Hard invariants (never violate these, in any phase)

These are checked at every step. If a design choice would break one, stop and ask.

**Sandbox**
- The agent operates only inside the resolved sandbox root (the launch directory, or an explicit `--sandbox <path>`).
- It must never read, write, delete, move, or execute files outside the sandbox root.
- All paths are canonicalized (resolve symlinks, `..`, env/shell expansion) **before** any use, and re-checked to be inside the root. Symlink targets that resolve outside the root are rejected.
- Subprocess working directory must be the sandbox root or a validated subdirectory — never outside.
- Block obvious escape patterns (`cd ..` past root, absolute paths outside root, `rm -rf /`, traversal) — but do **not** rely on string matching alone. Enforcement is on canonical resolved paths in the deterministic tool layer.
- Any escape attempt is blocked **and** logged. Even `dangerous` mode cannot escape the sandbox.

**Secrets**
- API keys are never placed in the model context, never printed, never written to logs or session transcripts, never spoken.
- The local config file holding keys is git-ignored by default.

**Trust boundary**
- The model *proposes* actions; the deterministic runtime *enforces* the rules. Treat every model-produced path, command, and argument as untrusted input and validate it.

**Voice privacy**
- Voice output and voice input are local/offline by default. No cloud TTS/STT, ever, unless the user explicitly opts in via config.
- Never send source code, file contents, shell output, secrets, or raw audio to any voice/cloud service by default.
- Never store raw microphone audio unless the user explicitly opts in. `Muted` mode records, transcribes, and stores nothing.
- The UI must clearly show when the mic is active and which mic mode is set.
- Only short, curated internal status strings are spoken — never raw model output (unless the user explicitly asks it to read something aloud).

## Tech stack (decided)

**Python 3.11+.** Rationale: the local voice stack (Piper TTS, faster-whisper/whisper.cpp bindings, `sounddevice`, `webrtcvad`) is mature and first-class in Python, which is the riskiest part of this build. If you strongly prefer TypeScript, raise it before Phase 0 — but default to Python.

- CLI: **Typer** (Click under the hood) for a clean command surface and `--help`.
- Models: **pydantic** v2 for config and structured types.
- Config: **TOML** via `tomllib` (stdlib read) + `tomli-w` for `jarvis init` writes.
- HTTP: `httpx` for provider calls.
- Tests: **pytest** (plus `pytest-asyncio` if the loop is async).
- Async event loop for the runtime so live steering and non-blocking voice work cleanly.
- Optional/lazy-imported, never hard requirements: `piper-tts`, `pyttsx3`, `faster-whisper`/`vosk`, `sounddevice`, `webrtcvad`. Gate every import; degrade to a Noop implementation when absent.

Packaging: `pyproject.toml` with a console-script entry point `jarvis = jarvis_code.cli.main:app`. `pip install -e .` must put `jarvis` on PATH.

## Build plan (phases)

### Phase 0 — Scaffold & toolchain
**Goal:** clone-and-run skeleton that installs `jarvis` and runs an empty test suite.

Build: repo layout above, `pyproject.toml` with the `jarvis` entry point and optional-dependency extras (`[voice]`, `[stt]`), `.gitignore` (must ignore `.jarvis/`, `.venv/`, `__pycache__/`, `*.onnx`, and the real config), `.jarvis.example.toml` with **placeholders only**, `CLAUDE.md`, a stub `jarvis --help`, and a passing trivial test.

**Done when:** `pip install -e .` then `jarvis --help` works; `pytest -q` passes; nothing real is committed as a secret.

---

### Phase 1 — Sandbox filesystem layer (security core)
**Goal:** a deterministic module that is the single chokepoint for all filesystem access.

Build: `sandbox/` with `resolve_sandbox_root(launch_dir, explicit_path)`, and a `Sandbox` object exposing safe primitives (`safe_path()`, `read`, `write`, `list`, `delete`, `move`, `mkdir`) that canonicalize and re-validate every path against the root, resolve symlinks and reject out-of-root targets, and raise a typed `SandboxViolation` (logged) on any escape. Validate subprocess cwd here too.

**Tests (required):** in-root paths pass; `..` traversal rejected; absolute out-of-root rejected; symlink whose target is outside root rejected; a path that's inside-then-symlinks-out rejected; cwd validation rejects out-of-root dirs.

**Done when:** all sandbox tests pass and no other layer touches the filesystem except through this module.

---

### Phase 2 — Config & secrets loader
**Goal:** load provider/voice config from TOML with env-var overrides, never leaking keys.

Build: pydantic schema mirroring `.jarvis.example.toml` (providers, `[voice]`, `[voice.input]`, `[voice.output]`). Load order: env vars override file values (`ANTHROPIC_API_KEY`, etc.). A secret-redacting logger so keys can never reach logs. `config path` / `config validate` helpers. Clear errors when config or a key is missing (see CLI messages below).

**Tests (required):** loads valid config; env override beats file; missing-config and missing-key produce the specified friendly errors; redaction verified — assert no key value appears in any log/transcript output.

**Done when:** config tests pass; grep your own logs in a test to prove zero key leakage.

---

### Phase 3 — Tool registry + permission manager
**Goal:** the full tool set, each routed through the sandbox and gated by mode.

Tools (all validate paths via Phase 1 first): `list_files`, `read_file`, `write_file`, `edit_file`, `delete_file`, `search_files`, `grep_text`, `run_shell`, `git_diff`, `git_status`, `create_directory`, `move_file`, `spawn_subagent`.

Permission modes — implement exactly three:
- **`plan`**: read/inspect/search/plan only. No writes, edits, deletes, shell, installs, or git mutations.
- **`auto`**: free reads; may propose edits and write **after showing a concise diff/summary and getting approval where appropriate**; must **ask before any shell command**, showing: command, working dir, why, expected effect, risk level. Approval menu is exactly **1) Yes  2) No  3) Do Something Else**. "Do Something Else" lets the user type instructions back to the model, which it uses to revise.
- **`dangerous`**: read/write/edit/delete/move/shell without per-action asking, **still confined to the sandbox**. Prints a clear startup warning.

`run_shell` executes with cwd = sandbox root or a validated subdir; reject any attempt to set cwd outside.

**Tests (required):** each mode allows/denies the right tool classes; shell gating in `auto`; the 3-choice menu including the "Do Something Else" feedback path; shell cwd cannot escape sandbox.

**Done when:** permission matrix tests pass for all three modes.

---

### Phase 4 — Model provider abstraction
**Goal:** one clean interface; swapping providers never touches the agent loop.

Build: a `ModelProvider` protocol (`complete(messages, tools) -> response` with text + tool-call parsing) and clients for **Anthropic, OpenAI, DeepSeek, Gemini, Vertex AI, Azure Foundry** (endpoint + key + model_name + api_version). Provider/model selected from config or `--provider`/`--model`. Keys pulled from the secrets layer and **never** placed in any context object the model can see.

**Tests (required):** provider selection from config and from flags; correct client constructed per provider (mock HTTP — no live calls in tests); a test asserting the assembled model context contains no key material.

**Done when:** selection + isolation tests pass with all six providers wired.

---

### Phase 5 — Agent runtime loop, context, sessions, memory
**Goal:** the loop that ties it together, with persistence and project memory.

Loop: load config → resolve sandbox → init session → load project memory (`JARVIS.md` or `.jarvis/memory.md`, treated as instructions but below explicit user instructions and safety rules) → build context → call model → parse text + tool calls → route through permission manager → execute allowed tools → append to transcript → check steering queue → compact if needed → repeat until complete/blocked/aborted.

Context management: include system instructions, user request, current mode, sandbox root, file summaries, recent tool results, current plan, prior key decisions. On overflow, summarize older tool results while preserving: goal, constraints, files changed, errors, commands run, pending tasks, permissions decided, sub-agent summaries.

Sessions: `.jarvis/sessions/` append-only JSONL recording prompts, model responses, tool calls/results, permission decisions, files changed, commands run, sub-agent summaries, errors. **Never** keys, raw secrets, or full env.

**Tests (required):** memory file loaded when present and correctly deprioritized; session JSONL written with the right records; **assert no secrets in any transcript**.

**Done when:** an end-to-end `plan`-mode run against a fixture repo produces a transcript and a plan, with green tests.

### Phase 6 — CLI surface & terminal UX
**Goal:** the documented commands and a clean interface.

Commands: `jarvis`, `jarvis "<task>"`, `jarvis --mode plan|auto|dangerous "<task>"`, `jarvis --sandbox <path>`, `jarvis --help`, `jarvis init`, `jarvis doctor`, `jarvis config path`, `jarvis config validate`, `jarvis voices list`, `jarvis voices test`.

`jarvis init` creates git-ignored `.jarvis/`, `.jarvis/config.toml`, `.jarvis/sessions/`, `.jarvis/voices/`. Friendly failures:
- No config → `No provider config found.\nRun: jarvis init\nThen edit: .jarvis/config.toml`
- No key → `No API key found for provider '<p>'.\nAdd it to .jarvis/config.toml or set <PROVIDER>_API_KEY.`

`jarvis doctor` checks (and prints pass/fail, **never** a key value): Python version, package install, `jarvis` on PATH, sandbox root, config presence, selected provider, key exists (boolean only), voice engine availability, Piper availability if selected, local STT availability if voice input enabled, mic permission if voice input enabled, git status if applicable.

Task UX: concise model text; clear step display; diffs/summaries before edits; the 3-choice permission menu; a finish summary of what changed, files touched, commands run, checks performed, remaining risks/TODOs.

**Tests (required):** `jarvis init` creates the right ignored tree; `jarvis doctor` runs and never prints a key.

**Done when:** the first-run flow works: `jarvis doctor` → `jarvis init` → `jarvis --mode plan "explain this project"`.

### Phase 7 — Voice output (local/offline)
**Goal:** spoken short status updates, local by default, non-blocking.

Build the interface and engines:
```
class VoiceEngine(Protocol):
    async def speak(self, text: str, options: SpeakOptions | None = None) -> None: ...
    async def stop(self) -> None: ...
    async def is_available(self) -> bool: ...
```
Implementations: **PiperVoiceEngine** (default, local neural TTS, downloadable `.onnx` voice models on disk), **SystemVoiceEngine** (OS TTS / `pyttsx3` fallback), **NoopVoiceEngine** (when nothing is available — silent, never crashes). Default voice preset name `"jarvis-inspired"`: calm, concise, technical, cinematic in *style only* — do not claim to clone any real actor/character voice.

Queue pipeline: agent emits a voice event → subsystem shortens the message → local synth → async playback → pending speech is cancellable on approve/deny/interrupt/continue. Speak only short curated strings ("Scanning the project.", "I found the failing test.", "Running the test suite.", "Launching a focused sub-agent.", "Launching the swarm.", "Requesting permission to run a command.", "Permission denied. Choosing another route."). In voice mode, permission requests are spoken aloud (e.g. "I need permission to run npm test inside the sandbox."); on approval, stop any in-progress speech immediately and continue.

Config honored from `[voice]` (engine, default_voice, model/config paths, fallback_engine, speech_rate, volume, announce_subagents, announce_permissions, swarm_phrase).

**Tests (required):** message-generation produces short curated strings (not raw model output); engine selection + Noop fallback; assert no file contents/secrets are ever passed to the engine.

**Done when:** `jarvis voices list/test` work and voice degrades cleanly to Noop with no Piper installed.

---

### Phase 8 — Voice input + STT + mic modes
**Goal:** local speech-to-text and the three mic modes, local by default.

Build: STT engine interface with a default local engine (**faster-whisper** or **Vosk**; modular so cloud STT is an explicit opt-in only). Mic modes **Open Mic** (continuous, with VAD/wake mechanism to avoid noise; configurable because some users won't want always-on), **Push to Talk** (records only while held — default `Space` to hold-to-talk / `V` to toggle; document the real choice), **Muted** (mic fully off — guarantee nothing recorded/transcribed/stored). Honor `[voice.input]` (enabled, mode, stt_engine, push_to_talk_key, wake_word_enabled, allow_cloud_stt). User can disable input while keeping output, and vice versa. Log only the text instruction if needed for continuity — never audio.

Terminal control shows the active mode, e.g. `Mic: [Open Mic] [Push to Talk] [Muted]` with the current one highlighted.

**Tests (required):** mode switching (Open Mic ↔ PTT ↔ Muted); Muted guarantees no capture; cloud STT stays disabled unless `allow_cloud_stt = true`; transcripts never contain audio.

**Done when:** mode-switching tests pass and input degrades cleanly when no STT/mic is present.

---

### Phase 9 — Event system, live steering & interrupts
**Goal:** concurrent steering while work proceeds.

Build an event-driven runtime with a live **instruction queue** and these events: `UserTextInput, UserVoiceInput, VoiceModeChanged, PermissionDecision, ToolStarted, ToolFinished, ToolFailed, AgentStepStarted, AgentStepFinished, SubAgentStarted, SubAgentFinished, InterruptRequested, SteeringInstructionReceived`.

Classify live user speech into: **steering** (fold into plan asap), **question** (answer briefly, keep working when possible), **soft interrupt** (finish current safe atomic step, then adjust), **hard interrupt** (stop current action if safe), **permission response** (route to the active prompt). Drain the queue at safe checkpoints: before model call, before tool exec, after tool result, before file writes, before shell, before spawning sub-agents, before finalizing.

Long-running shell: support cancellation; if cancellable, stop safely; if not, tell the user it'll stop at the next safe point. If a permission prompt is active, interpret voice first as a possible permission response, integrating with the same 1/2/3 menu ("Do Something Else" collects spoken instruction as steering) — no parallel permission system.

Keyboard controls (document the real ones in README): `M` cycle mic mode, `V` toggle PTT recording, `Space` hold-to-talk in PTT mode, `Esc` soft interrupt, `Ctrl+C` hard stop/exit, `?` show controls.

**Tests (required):** steering queue ordering and safe-checkpoint draining; voice-as-permission-response; mic-mode-change events.

**Done when:** steering and interrupt tests pass and a steering instruction measurably alters the next step.

---

### Phase 10 — Sub-agent orchestration
**Goal:** spawnable sub-agents in isolated contexts.

Build types: **explorer, planner, debugger, reviewer, implementer, verifier**. Each runs in its own context window, inherits the same sandbox root and permission mode, **never exceeds the parent's permissions**, and returns a concise summary to the parent (not its full transcript). Voice announces "Launching a focused sub-agent." or the configurable `swarm_phrase` ("Launching the swarm.").

**Tests (required):** sub-agent cannot get more permissions than parent; sub-agent confined to same sandbox; parent receives summary, not raw transcript.

**Done when:** permission-inheritance and isolation tests pass.

### Phase 11 — Docs, final doctor, polish
**Goal:** clone-and-run quality.

`README.md` with: Quick Start (clone → `pip install -e .` → `jarvis doctor` → `jarvis init` → first command), Security Model (everything confined to sandbox root; model proposes, runtime enforces), provider setup for **Azure Foundry, Vertex AI, Gemini, Anthropic, OpenAI, DeepSeek**, local Piper TTS setup, local STT setup, Open Mic / Push to Talk / Muted explanation, permission prompts, examples, and the documented keyboard controls. `docs/` for deeper notes. Final pass on `jarvis doctor` to cover everything in Phase 6's list.

**Done when:** a fresh clone reaches a working `jarvis --mode plan` run using only the README, and the full test suite is green via one command (`pytest -q`).
